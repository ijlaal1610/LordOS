# Changelog

All notable changes to LordOS are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and LordOS
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Pre-releases carry a
suffix (`-beta`) and are published on GitHub as pre-releases. Each section below is also the body
of the matching [GitHub release](https://github.com/lordbasex/LordOS/releases), generated by
`tools/release/release-notes.sh` (see [docs/RELEASING.md](docs/RELEASING.md)).

## [Unreleased]

## [0.8.4] - Unreleased

### Added

- **Settings → Appearance → «Browsers: tabs in the title bar».** One switch for both preinstalled
  browsers: on (the default), Chromium and Firefox draw a single bar with their tabs and LordOS's
  window buttons; off, they use the LordOS frame. It changes the setting in your own browser
  profiles and applies the next time each browser opens; if Chromium is open, it waits until you
  quit it. Chromium profiles from before this version that still use the LordOS frame are shown on
  the page, with a button to change them too. A choice you made yourself in a Firefox `user.js`
  file is left alone, and choices you make later in the browsers' own settings stick.
- **Remote desktop as video.** In a browser that supports WebRTC, the remote desktop now arrives as
  real video (H.264, or VP8 when the browser has no H.264) with the session's sound (Opus), instead
  of images. Still areas are then made pixel-perfect with lossless tiles, so text stays sharp.
  Dragging a window went from about 23 frames per second and 12.5 Mbit/s to about 28 frames per
  second and under 1 Mbit/s, and the connection's own process from 57 % of a core to 2 %. The
  session encodes once (on the graphics card with VA-API when it can, else in software) for every
  viewer of that session; the screen keeps being composed on the graphics card while someone
  watches. Keyboard, mouse and clipboard go over a WebRTC data channel. If the browser or the
  network can't do WebRTC, it falls back to the images, as before.
- **Settings → Sharing → Video:** turn the video off (images only), add public STUN servers and a
  TURN relay for connecting across networks. A built-in STUN server covers the local network, and
  nothing reaches outside servers unless you add them. The relay's password stays on the computer,
  readable only by the system, and is never sent to the browser.

### Changed

- **Browsers with a single top bar.** Chromium and Firefox now draw their own bar, with the tabs in
  the title bar and the window buttons inside it, instead of the LordOS frame on top. In Chromium
  the buttons are LordOS's traffic lights (from LordOS's GTK theme, sized like LordOS's own frame);
  Firefox keeps its own button style. Both put them where the LordOS theme does: on the left in Lord
  Default, on the right in Classic, and follow a theme or light/dark change live. Going back to the
  LordOS frame is one switch in each browser («Use system title bar and borders» in Chromium,
  «Title Bar» in Firefox), and it now applies right away, without reopening the window. Systems
  upgraded from 0.8.3 get the new defaults for Firefox, and for new Chromium profiles; an existing
  Chromium profile keeps its frame until its user switches (or uses the new switch in Settings).

### Fixed

- **Two title bars in Chromium.** With «Use system title bar and borders» off, Chromium drew its own
  bar and LordOS still put its frame on top: the compositor now honors the frame an app asks for
  (xdg-decoration and the GTK 3 decoration protocol), also when it changes while the window is
  open; the window keeps its place, size, maximized state, focus and Dock entry.
- **Linux app windows disappeared after switching between Lord Default and Classic** (they stayed
  open but invisible): they now come back in the new theme, maximized ones still maximized.
- **The window menu of apps that draw their own bar.** A right click on a GTK app's own title bar
  now opens the theme's window menu (Minimize, Zoom, Close; in Classic also Restore, Snap layouts
  and the snap halves).
- **Raspberry Pi 5: blocking an app now closes its open connections** (a known issue in 0.8.3),
  as on a PC, instead of leaving them stalled until the app's own timeout. The LordOS Pi kernel is
  rebuilt as `6.18.57-lordos.3-rpi-2712` (`6.18.57-3+lordos`): the same Raspberry Pi source and
  options as before (Landlock, the BPF LSM, BTF, Yama) plus sock_diag socket destroy
  (`CONFIG_INET_DIAG_DESTROY`, `CONFIG_INET_UDP_DIAG`), so `lord-netperm` closes TCP and QUIC
  connections a new rule denies within a fraction of a second. Each kernel revision now installs
  as its own package next to the previous one, so the previous kernel stays bootable as a fallback
  (one line in `config.txt`, see [docs/RASPBERRY.md](docs/RASPBERRY.md#switching-kernels-on-a-board)).
  The image build and `verify-board` check the kernel has it. On a Pi 5: TCP downloads and an idle
  session end 0.04–0.37 s after the rule changes, an HTTP/3 (QUIC) download 0.08 s.
- **`build-kernel.sh` cross-compiles** the Pi kernel on an x86-64 Debian 13 (the arm64 Debian
  packages, no arm64 build dependencies needed).

## [0.8.3-beta] - 2026-10-19

### Added

- **X11 apps.** Programs that only speak X11 (xterm, Java/Swing apps, many games and older tools)
  now open in LordOS through Xwayland (the `xwayland` package), with the theme's window frame, their
  icon in the Dock (matched to their launcher by `WM_CLASS`), menus and tooltips above everything,
  fullscreen, minimize and close, and LordOS's cursor. Xwayland only starts when an X11 app
  connects and stops 10 seconds after the last one closes. LordOS's own X window manager is
  written in C and speaks the X11 protocol itself, without new libraries in `lord-server`.
- **Clipboard with X11 apps**, both ways, for the normal clipboard and the primary selection
  (select to copy, middle click to paste); large copies and images included.
- **Primary selection for Wayland apps** (middle-click paste between GTK, Qt and other apps).
- **Classic, a second full appearance.** The Classic theme is no longer a template: it is a
  complete desktop for people used to a taskbar layout, with the same apps as Lord Default. A
  centered taskbar (or aligned to the start, on any side of the screen) with the start button,
  search, task view, the pinned and open apps and the Trash last; a start menu with a search field
  that searches like the system search (apps, settings, files, notes, the calculator, Help), a grid
  of pinned apps you arrange with a right click, recently used apps, every app A–Z, and the user
  and power button (Lock, Switch User, Log Out, Restart…, Shut Down…); a tray with quick settings
  (network, Bluetooth, Do Not Disturb, Night Light, dark mode, transparency, volume, what is
  playing, battery) and a notification panel with a month calendar; notifications above the
  taskbar; and a window frame with the title at the start and the buttons at the end. Everything
  is our own design: LordOS icons drawn by the theme, Inter, the LordOS wallpapers and names.
  Switch between the two in **Settings → Appearance → Desktop style**, live and without logging
  out: the windows that were open come back in the new one. Light and dark mode, right-to-left
  languages and the accent colors work in both. See [docs/DESIGN.md](docs/DESIGN.md), "Classic".
- **Window snapping.** In Classic, drag a window to the left or right edge to fill that half of the
  screen, to a corner for a quarter, or to the top edge to maximize it; a preview shows where it
  will go. Hovering over the maximize button offers layouts (halves, two thirds and one third,
  thirds, quarters), and Super+arrows move the window in front between them. Dragging a snapped
  window away gives it back its size. See [docs/WINDOWS.md](docs/WINDOWS.md), "Snapping".
- **Task view.** Super+Tab (or the taskbar button) shows every window side by side, live and
  smaller, over a dimmed desktop: click one to bring it to the front, or close it from there.
- **Themes restyle every app.** The shared controls (buttons, fields, segmented controls, sidebars,
  menus, tooltips, grouped forms, confirmations and the Restart/Shut Down sheet) now take their
  shape from the theme: corner radii, a light or accent menu highlight, an accent bar or a fill for
  the selected sidebar row, an underline or a ring on the focused field, and bordered buttons. Lord
  Default looks as before; Classic uses smaller radii, borders and subtle highlights. Isolated
  apps (Mail, Calendar, Contacts, Reminders, Passwords) follow it too.
- **Remote desktop: allowlist, blocklist and temporary blocks.** Settings → Sharing chooses who
  may connect: the **local network** (the default: private and link-local addresses and
  connections over a VPN of this computer), **only these addresses** (the allowlist), or **any
  address**; keeps a **blocklist** of addresses and networks that are always refused; and lists the
  **temporarily blocked** addresses with the time left, **Unblock** and **Block permanently**. You
  get a notification when an address is blocked.
- **Monitor → Network shows the remote desktop** as one more app while it's on: the browsers
  connected with their traffic, the recent failed sign-ins (address and the name typed, for
  administrators), the blocks and the lists, with Block and Unblock.

### Changed

- Settings → Desktop & Dock in Classic adds **Taskbar alignment** (center or start).
- The `lordos` package recommends `xwayland`, and the ISO and the Raspberry Pi 5 image include it,
  so X11 apps open out of the box.
- The theme engine paints a scaled window that contains a blurred surface (a translucent
  Terminal) at its scaled size; its blur then only shows the window's own content. Before, such a
  window was drawn at full size during the Dock's minimize effect.
- **Scroll bars stay out of the way.** Scroll bars across the system are now thin overlay bars
  drawn at the very edge of a list or panel: hidden until you scroll (mouse wheel, touchpad,
  keyboard or dragging the bar) or bring the pointer near the edge, 6 px wide and 10 px under the
  pointer, fading out a second after the last scroll. They no longer take a strip of their own and
  never cover text. Settings → Appearance → **Show scroll bars**: *Automatically* (the default),
  *When scrolling* or *Always* (the persistent bar, for accessibility). With Reduce motion they
  appear and disappear without a fade; in right-to-left languages they are on the left. The
  Classic theme draws them with its own squarer style, and the Terminal's history bar matches.
- **Monitor → Network: a tidier detail panel.** The right panel's sections (Process, Rule,
  Connections, Data, Ports and protocols, Destinations, and the summary's) fold with a click on
  their header and stay folded the next time. App names in "Top apps by traffic", the app list and
  the panel header wrap to two lines instead of being cut, long destinations wrap too, and the app
  list gives the name more room (the counts moved next to the traffic bar, the Data and Rule
  columns are narrower).
- **Debian's smartd stays off.** Installing smartmontools from Disks no longer leaves its
  monitoring daemon polling the disks every 30 minutes; Disks and the Monitor read SMART on demand.
  Administrators can opt back in (docs/SYSTEM.md, "smartd").
- **Remote desktop now accepts the local network only by default.** Connections from public
  internet addresses are refused unless you choose **Any address** (or list them) in Settings →
  Sharing; a VPN of this computer still works. Browsers signed in before the update sign in once
  more (the sign-in cookie changed).

### Security

- X11 apps run in their app's scope, so per-app firewall rules and the Monitor apply to them.
- X11 apps never see Wayland apps, LordOS's screen, Passwords or the keyring prompt, nor the keys
  typed into them; what is copied outside X enters X only while an X window has the keyboard, and
  passwords copied in Passwords never do. Synthetic input between X11 apps (XTEST) is off.
  Xwayland runs without network, in its own scope. X11 apps can still see each other, as in any X11
  desktop (see the privacy documentation).
- Apps with device or "no files" restrictions get no X display.
- Clipboard offers to Wayland apps are bound to the selection they were made for and to the app
  with the keyboard.
- **The per-app firewall applies to open connections, not only to new ones.** A rule change used to
  leave established TCP connections and connected UDP sockets (QUIC) outside the policy until they
  closed. `lord-netperm`'s packet filter (the cgroup programs that already counted bytes per app)
  now takes the same decision as at connect time for every packet of an app whose rules deny
  something, and `lord-netperm` destroys those sockets over sock_diag netlink (its unit now also
  allows `AF_NETLINK`; it still creates no internet sockets). "No incoming connections" now also
  cuts connections already accepted. The Raspberry Pi kernel build enables
  `CONFIG_INET_DIAG_DESTROY`; on a kernel without it the packets are still dropped.
- **Remote desktop: 3 failed sign-ins block the address.** For 15 minutes, then 1 hour, then 24
  hours if it happens again within a day (IPv6 counted per /64). Blocked addresses are cut before
  any TLS work and stay blocked after a restart (`/var/lib/lordos/remote/blocklist`, root only).
  Accounts are never locked (that would let anybody lock you out); repeated failures for one
  account only slow it down. Every failure and block goes to the journal (address and a sanitized
  user name, never the password).
- **Remote desktop: a full security review and hardening** ([docs/REMOTE.md](docs/REMOTE.md#security-analysis-083)).
  The page and the server check every field strictly (user names `a-z 0-9 _ -` up to 32, passwords
  1–1024 bytes); the request, the form, the cookie, the WebSocket and the input messages are parsed
  strictly and refused otherwise; a wrong user name and a wrong password take exactly the same time;
  connections that are slow, too many from one address, or from addresses not allowed are closed
  early; the sign-in cookie is a `__Host-` cookie stored only as a hash, tied to the password (a
  password change or lock ends it) and ended for every browser of a user when that user locks the
  screen; sign-in and sign-out only accept requests from the page itself; TLS 1.2+ with AEAD
  ciphers only; the part that serves the desktop runs as the user with no shared state, no other
  descriptors and no way back to root. root can never sign in remotely.

### Fixed

- Java (AWT/Swing) windows were blank or shifted (non-reparenting window manager).
- The Passwords and Backups icons sat off center in the Dock and the launcher.
- **Blocking an app now cuts the connections it already has open.** Turning an app's rule off in
  Monitor → Network (or adding a deny rule for a destination or domain, or a restriction such as
  "no internet") counted its new connections as denied, but what was already open kept flowing:
  a video kept playing over its established TCP and QUIC connections. Now the matching traffic stops
  within milliseconds: the kernel drops the packets of those connections and LordOS closes them, so
  the app sees the connection end instead of a stall. Only what the new rule denies is cut: other
  destinations, the local network under "no internet", and the clients of a server the app runs
  keep working. Switching the rule back to allow works again at once. The Monitor counts every cut
  connection as denied and shows the dropped bytes as "Blocked traffic" in the app's details. See
  [docs/FIREWALL.md](docs/FIREWALL.md), "Existing connections are cut".

### Known issues and limitations

- **X11 apps need Debian's `xwayland` package.** New installs from the ISO and the Raspberry Pi 5
  image, `install.sh` and `apt upgrade` bring it (the `lordos` package now recommends it). The
  Store's update installs only what the package depends on, so after updating from the Store,
  install **xwayland** from the Store (or `sudo apt install xwayland`) to open X11 apps; Wayland
  apps don't need it. For the same reason `apt-get upgrade` keeps `lordos` back; `apt upgrade`
  (or `apt-get install lordos`) installs it.
- **Raspberry Pi 5: blocked connections stall instead of closing.** The image keeps 0.8.2's
  LordOS kernel, which was built before `CONFIG_INET_DIAG_DESTROY`; there the firewall drops the
  packets of a connection a new rule denies at once, but the app only sees the connection end at
  its own timeout. The next Pi kernel build closes them like on a PC.
- X11 apps can see each other, as on any X11 desktop; a separate display for restricted X11 apps,
  drag and drop between X11 and Wayland apps and sharp X11 apps on HiDPI displays come later.
- The other known issues of 0.8.2 still apply.

### Upgrading

- **From 0.8.2 or 0.8.1:** Store → Updates shows "LordOS 0.8.3 is available" with these notes;
  **Update** installs it, and a restart finishes it. `sudo apt update && sudo apt upgrade` does the
  same. The update runs migration 004 once (it stops Debian's smartd if smartmontools left it
  running; from 0.8.1, migration 003 runs first); `ls /var/lib/lordos/migrations` lists the ones
  applied. Your settings are kept.
- **Remote desktop after the update:** connections from public internet addresses are refused
  unless you choose **Any address** (or add them to the allowlist) in Settings → Sharing; the local
  network and a VPN of this computer keep working. Browsers that were signed in before sign in
  once more.
- **From 0.8.0 (once):** run `curl -fsSL https://lordos.org/install.sh | sh` (a system installed
  from the 0.8.0 ISO has no `curl`: run `sudo apt update && sudo apt install -y curl` first). It
  upgrades in place to 0.8.3, runs migrations 001 to 004 and adds the LordOS repository; from then
  on new versions come through Store → Updates.

## [0.8.2-beta] - 2026-10-19

### Added

- **New wallpapers.** Eleven original LordOS wallpapers in three categories: **Signature** (Crystal
  Crown, Eternal Dawn, Royal Flow, Royal Waves, Violet Horizon), **Lumo** (Celestial, Aurora) and
  **Cosmos** (Event Horizon, Infinite Galaxy, Solar Odyssey, Stellar Voyage), created by iPERFEX
  with an AI image generator. Settings → Wallpaper now lists every wallpaper grouped by category,
  with the previous four gradients as "Gradients". They are installed once in
  `/usr/share/backgrounds/lordos/` as high-quality JPEG (about 4 MB in total) with small thumbnails
  for the pickers, and a higher-resolution version added later is used automatically on the
  screens that need it.
- **Suggested for your computer.** Store → Discover now starts with packages for the hardware
  LordOS finds in the computer, each with the reason it appears ("We detected a printer from HP
  connected by USB"): the guest tools of a VMware or QEMU virtual machine, the proprietary graphics
  driver for an NVIDIA card (labeled as not free software, never preselected, with what changes:
  DKMS, Secure Boot key enrollment, older cards, and that the free nouveau driver stays the
  default), vendor drivers for USB printers and scanners, driverless USB printing (`ipp-usb`),
  the Raspberry Pi 5's board tools, and the firmware package a Wi-Fi, Bluetooth, network or
  graphics device asked for and didn't find. One click shows the usual plan and installs through
  the package engine; "Don't suggest again" hides a card for good. When something new is
  suggested, the Store's Discover item shows a count and one notification says so. For a
  VirtualBox virtual machine the card explains that its guest utilities aren't part of Debian 13.
  Detection only reads the kernel's hardware files; nothing is sent anywhere. The rules are data
  (`assets/store/suggestions.json`); see [docs/PACKAGES.md](docs/PACKAGES.md).
- **Monitor → Disks: each disk's temperature and health.** The Disks tab now shows every physical
  disk's live temperature, read from the kernel without root: NVMe and M.2 drives through the nvme
  driver's own sensor (also on a Raspberry Pi 5 with an M.2 HAT), SATA disks through the `drivetemp`
  module, which the `lordos` package now loads at boot. Memory cards, virtual disks and adapters
  without a sensor say "No sensor", never a made-up value. The chosen disk gets a 30-minute
  temperature chart with the drive's own limits when it reports them, and an OK / Check / Failing
  light from a cached SMART summary, with "Open in Disks". Spinning disks are only read while they
  are in use, so a resting disk is never woken up
  ([docs/MONITOR.md](docs/MONITOR.md#disk-temperature-and-health-082)).
- **Disks: the full SMART report with smartmontools.** The first time, the health card offers to
  install Debian's smartmontools through the Store's package engine (an administrator). Then it
  shows the overall health and why in plain words, temperature and limits, SSD wear (% of its rated
  life used), power-on hours and cycles, reallocated and pending sectors, every attribute with a plain
  name, the NVMe health log, the error log, the disk's own temperature history, and short and long
  self-tests with progress and results. USB disks behind adapters that pass SMART through work too.
  `smartctl` runs only through four new closed, validated root helper actions (`smart-info`,
  `smart-health`, `smart-test`, `smart-abort`) on real whole disks, at a fixed path, with JSON output
  ([docs/SYSTEM.md](docs/SYSTEM.md#smart-with-smartmontools-082)).
- **Notifications when a disk gets too hot or its health gets worse**, at most once per disk every
  30 minutes for heat, and only when the health is worse than last seen. On by default, with a switch
  in Monitor → Disks.
- **Smooth video in the browser without hardware decoding.** Video sites that send VP9 or AV1
  make the browser decode them on the processor when the graphics card can't (virtual machines,
  older PCs, the Raspberry Pi 5), and the video stutters. LordOS now checks at every boot what the
  hardware decodes (VA-API profiles through `lord-media`, V4L2 memory-to-memory decoders on ARM,
  virtual graphics cards count as "no"; cached per boot) and, when VP9 or AV1 is missing, asks the
  browsers for H.264 instead, which is far lighter to decode. Settings → Displays → Video in the
  browser: "Optimize video for this computer" (Automatic by default, Always, Never) and "Lower
  quality automatically when video stutters" (off by default). Nothing is sent anywhere
  ([docs/VIDEO.md](docs/VIDEO.md)).
- **Our own small browser extension** (`/usr/share/chromium/extensions/lordos-video`, MIT), loaded
  by Debian's Chromium: on YouTube it reports VP9/AV1 as unsupported so the site sends H.264, and
  when a video keeps dropping frames it shows a small notice that offers a lower quality (or lowers
  it by itself, if enabled). Its settings come from a managed policy written by the closed admin
  action `video-optimize` (fixed text, no user text). Firefox ESR only loads signed extensions, so
  for now it gets AV1 turned off through a default preference (it then uses VP9); the extension
  for Firefox waits for signing.
- **Allow or block each destination inside Monitor's app rows.** Open an app in Monitor → Network
  and every name it reached (or address, when the system resolver gave no name) has its own
  allow/block switch, showing what the app's rules decide for it right now and why ("By the rule
  \*.example.com", "Follows this app's default", "Blocked by this app's restrictions"). A click
  writes, flips or removes the rule for exactly that name, the same rule Settings → Privacy →
  Network rules by app shows, and `lord-netperm` applies it at once. Long lists show eight and
  "N more…"; rows keep their place while the list is open
  ([docs/MONITOR.md](docs/MONITOR.md#per-destination-switches-082)).
- **Traffic history.** The Network tab's chart now zooms out from the live minute to 1 hour,
  24 hours, 7 days and 30 days, steps back and forward one window at a time and has **Now**; with
  an app selected its own chart follows the same window, and the summary lists the apps that moved
  the most in it. Your session records bytes received and sent per minute (7 days) and per hour
  (30 days), for the computer and for each of your apps, in a small file in your home folder
  (`~/.local/state/lordos/net-history.bin`): never an address, a name or a country. Settings →
  Privacy → Monitor has **Keep a traffic history** (on) and **Clear History**
  ([docs/MONITOR.md](docs/MONITOR.md#traffic-history-082)).
- About LordOS shows a "System app" badge and the state of the system code: "Verified", or
  "Development build" for an unsigned development tree.
- `lord-server --check-code [<folder>]` checks a whole installed tree against the signed manifest
  (troubleshooting, and the `.deb` build).
- SHA-256 uses the CPU's SHA-256 instructions on the Raspberry Pi 5 (5× faster there), and the
  portable code is about twice as fast.
- **Design study: an immutable LordOS with A/B system images** ([docs/IMMUTABLE.md](docs/IMMUTABLE.md)).
  It compares dm-verity system partitions, fs-verity, composefs, OSTree, A/B root partitions and
  btrfs snapshots against Debian 13, the Store, the Raspberry Pi 5 and LordOS's threat model, and
  recommends a separate, optional edition: a read-only `/usr` verified by dm-verity in two slots,
  one signed boot image per version, automatic fallback to the previous version when an update
  doesn't start, and `/etc` and the home folders kept on their own partition. The classic edition,
  `install.sh` and in-place updates stay as they are; there is no conversion of existing systems.
- **Experimental build of that design** (`tools/immutable/`, not part of the regular ISO or
  Raspberry Pi image): a disk image for UEFI virtual machines with the A/B layout, a signed
  update into the other slot, and a scripted demonstration in which a deliberately broken version
  fails three times and the machine returns to the previous version on its own. Its payload is a
  minimal Debian 13, not the LordOS desktop yet; the rest of the plan moves to later versions.

### Changed

- **New default wallpaper:** new users start on **Celestial**; anyone who already chose a wallpaper
  keeps it. The login screen (and the remote login page) now shows **Crystal Crown**.
- The Control Center shows the current wallpaper and three from the collection; the rest are in
  Settings → Wallpaper (**Change Wallpaper…**).
- **The map's moving dots are cheaper to draw:** they are small ready-made images and the map's
  frame is opaque, so a repaint starts there. Repainting several small rectangles per frame instead
  of the one box around every change (which halved the animation's cost in our measurements) is in
  this version but **off by default**: in one test a minimized window left a grey rectangle on the
  screen, and correctness comes first. `LORD_DAMAGE=multi` in lord-server's environment turns it
  on for testing ([docs/MONITOR.md](docs/MONITOR.md#082-several-damaged-rectangles-vm-119)).
- Isolated apps start faster: the app host is compiled to bytecode once per session, so an app's
  JavaScript loads in ~23 ms instead of ~110 ms (Mail's window: ~145 ms from the click to its first
  frame on a 1.8 GHz test machine).
- The Dock's quick actions and **New window** now work for the apps that run in their own process;
  Passwords stays a single window.
- An isolated app's process is named after the app (`mail`), not `exe`, in `ps` and Monitor.
- Releases: `tools/release/sign-code.sh` signs the system-code manifest on the maintainer's machine
  before the build; `make -C server RELEASE=1` builds a lord-server that only runs signed code, and
  `tools/iso/mkdeb.sh` refuses to package bundles that don't match
  ([docs/RELEASING.md](docs/RELEASING.md)).

### Fixed

- **Long notes no longer overlap.** In a row with a part that grows (a list item's text next to its
  bullet), the layout engine measured that part's wrapped height at the whole row's width, so the
  last line of a long bullet could be drawn over the next one (Store → Updates, "What's new", and
  any Markdown list). It is now measured at the width it is drawn at.
- The app host's read and hash for isolated apps' bytecode moved off the main thread at session
  start (about 15 ms on a cold start); the bytecode is still compiled from exactly the verified bytes.
- **Package lists after enabling a component.** Adding a component (such as `non-free-firmware`)
  or a source whose signed release file hadn't changed upstream left the package list as it was
  ("already up to date"); the index is now rebuilt whenever the set of lists it is built from
  changes.
- Isolated apps showed times in UTC instead of the local time zone.
- Trusting a self-signed certificate for an SMTP server on port 465 pinned it as the IMAP server's,
  so sending kept failing.

### Security

- **Keys typed into LordOS's own prompts no longer reach the Linux app in front.** What you typed
  into the search, the app launcher, a sheet or a system prompt (the keyring password, a permission
  prompt, the file chooser) was also delivered to the Linux (Wayland) app whose window was in front,
  so that app could read a password typed into the keyring prompt. While any of them is open, Linux
  apps now get no keys at all; menus and the clipboard and emoji panels still type into the app
  ([docs/PRIVACY.md](docs/PRIVACY.md#system-prompts-take-the-keyboard-082)).
- **Mail, Calendar, Contacts and Reminders run in their own sandboxed process.** Like Passwords
  and installed apps, each one is now `lord-server --app <id>` with Landlock, seccomp, no network
  and its own cgroup scope, instead of running inside the desktop's process. Mail's window can read
  only its own data folder; your files reach it only through the system's open/save dialog; it
  cannot open sockets, read the mail cache, the accounts file, `~/.ssh` or other apps' data (checked
  from inside the running process). They reach `lord-maild` only through `lord-server`, each with
  its own list of allowed requests (Calendar cannot read mail) and its own replies and events.
  Notifications, alarms, Dock quick actions, several windows and opening attachments keep working.
  Monitor shows each app as its own process with its name and icon, and the firewall's per-app
  restrictions (`lpk:mail`, …) apply to it ([docs/PRIVACY.md](docs/PRIVACY.md#system-apps-in-their-own-process-082)).
- **LordOS checks its own code before running it.** Every bundle LordOS runs as its own code — the
  themes with the shell and every native app, the login screen, the app host of isolated apps and
  the system apps that run as their own process — is listed with its SHA-256 in
  `/usr/lib/lordos/code-manifest.json`, signed with the LordOS release key (Ed25519).
  lord-server verifies the signature with the public key compiled in, and the hash of each bundle
  as it loads it, from the same read (no window to swap the file). A bundle that doesn't match is
  not run: the desktop falls back to another theme and shows "This LordOS component was modified and
  was not loaded"; with nothing left to load (or at the login screen) a built-in recovery screen
  explains it and how to repair it, never a blank screen. It protects against changes by non-root
  processes and offline modification; root can still replace lord-server itself, which phase 3
  (fs-verity, A/B images) will cover. Cost on a session start: about 7 ms on a Raspberry Pi 5,
  18–34 ms on a 1.8 GHz Xeon VM
  ([docs/SIGNING.md](docs/SIGNING.md#verified-system-code-082)).
- **System apps can't be removed.** Store → Installed shows "System app — part of LordOS" instead
  of Remove for the apps that come with LordOS, and the `lordos` package is marked `Protected` so the
  Store's package engine refuses to remove it.

### Known issues and limitations

- **City names on the map.** Debian 13 only ships country-level IP databases (`geoip-database`) and
  LordOS's own is country-level too, so labels stay countries; no large download was added.
- **Repainting several small rectangles per frame is off by default** (see Changed): in one of five
  tries a window minimized over Monitor's animated map left a grey rectangle until it came back,
  and the cause is still being looked for. The desktop repaints as in 0.8.1.
- **Firefox ESR** gets AV1 turned off but not the video extension, which needs signing first.
- **The immutable edition** is a study and an experimental image for virtual machines; its payload
  is not the LordOS desktop yet.
- The other known issues of 0.8.1 still apply.

### Upgrading

- **From 0.8.1:** Store → Updates shows "LordOS 0.8.2 is available" with these notes; **Update**
  installs it, and a restart finishes it. `sudo apt update && sudo apt upgrade` does the same. The
  update runs migration 003 once (it loads the `drivetemp` module for SATA disk temperatures);
  `ls /var/lib/lordos/migrations` lists the ones applied. Your settings are kept, and a wallpaper

  from the 0.8.0 ISO has no `curl`: run `sudo apt update && sudo apt install -y curl` first). It

## [0.8.1-beta] - 2026-10-19

A maintenance and polish release on top of 0.8.0-beta, and the first one that installed systems
can update to in place: from here on, new versions arrive through **Store → Updates** (or `apt`)
from a signed LordOS repository, with no reinstall. It also brings a Dock you arrange yourself,
remote login over SSH from Settings, Restart and Shut Down in the crown menu, process actions and
complete traffic accounting in Monitor, Bluetooth on the Raspberry Pi 5, and fixes for typing lag
and black windows on the GPU path and for legacy BIOS boot in virtual machines.

### Added

- **A Dock you arrange yourself.** Drag any app (a LordOS app, an installed package or a Linux
  app such as Firefox) from the app launcher onto the Dock and it lands where you drop it; drag icons
  along the Dock to reorder them (the neighbours slide aside); drag one away and hold it for a
  moment to remove it with a "poof", or use **Keep in Dock** / **Remove from Dock** in the menus.

- **Update LordOS from the Store, without reinstalling.** Store → Updates now shows "LordOS
  <version> is available" with the release notes and an Update button, next to Debian's updates;
  files, settings and accounts are kept, and a "Restart required" notice appears when the new
  version (or a new kernel) is installed. It works the same on the ISO install, the Raspberry Pi
  image, Debian with `install.sh` and servers, and `sudo apt update && sudo apt upgrade` does the
  same. An optional daily check (on by default, never installs anything) notifies when something

- **Settings → Sharing → Remote login (SSH).** A new switch, off by default on every install,

  page shows `ssh <user>@<address>` for this computer and its ED25519 host key fingerprint, and
  lets you allow all users or only administrators. Root never logs in (`PermitRootLogin no` in a
  drop-in shipped by the `lordos` package). The Raspberry Pi image's `ssh` switch file keeps
  working and shows up as on ([docs/REMOTE.md](docs/REMOTE.md#remote-login-ssh)).
- **Restart… and Shut Down… in the crown menu** (and behind a Power button in the Classic theme's
  start menu); before, they were only on the login screen. Each opens a confirmation that does it

  are logged in. The session asks `lord-sessiond`, which only accepts those two words: any user may
  do it alone, and only an administrator while other users have sessions open
  ([docs/SESSIONS.md](docs/SESSIONS.md#restart-and-shut-down-from-a-session)).
- **Monitor → Processes: stop a process and Get Info.** Select a row and use the new Stop and
  Info buttons, the right-click menu, a double click, ❖/Ctrl+I or Delete. Stop asks first, with
  **Quit** (SIGTERM), **Force Quit** (SIGKILL) and Cancel. Your own processes are signalled by the
  session itself with `pidfd_send_signal` after checking the process's start time, so a reused PID
  is never hit; another user's or root's need an administrator and go through two new fixed,
  validated root helper actions (`proc-signal`, `proc-info`). PID 1, kernel threads, your
  session, LordOS's services and helpers and PipeWire can't be stopped: the sheet explains why.
  Get Info shows memory (real, virtual, shared, private, proportional), statistics (parent, group,
  CPU time, threads, context switches, page faults, start time, nice, control group and LordOS
  restrictions), open files and ports (with the addresses of each socket), the executable and the
  command line, updated every second ([docs/MONITOR.md](docs/MONITOR.md#process-actions-081)).
- **Bluetooth on the Raspberry Pi 5 image.** The on-board CYW43455 controller (on a UART, brought
  up by the kernel) now works out of the box: the image ships BlueZ, the chip's firmware patch
  (`bluez-firmware`), headset audio in PipeWire (`libspa-0.2-bluetooth`) and a small helper of our
  own, `lordos-rpi-bt@hciN`, that routes call audio (SCO) over HCI so headset microphones work.

  board is still to be tested ([docs/RASPBERRY.md](docs/RASPBERRY.md#bluetooth)).
- **Guest tools on VMware.** The ISO (and so every installed system) ships `open-vm-tools`:
  shutdown and restart from the hypervisor, time sync and the guest's IP address. Its services only
  run under VMware. Shared clipboard and automatic screen resize are not supported yet
  ([docs/ISO.md](docs/ISO.md#firmware-and-displays)).
- **A signed LordOS package repository** at `https://lordos.org/apt` (suite `stable`, amd64 and
  arm64), signed with a dedicated OpenPGP key (Ed25519, fingerprint
  `1DDA F390 107D F264 FA8A 0918 3972 CC6D E4DA 2336`) shipped as
  `/usr/share/keyrings/lordos-archive-keyring.gpg`; the `lordos` package adds
  `/etc/apt/sources.list.d/lordos.sources` and removes it when uninstalled. Built and signed on the
  maintainer's machine by `tools/release/apt-repo.sh`, tested on a staging path first.
- **Migrations between versions.** The package's `postinst` applies each version's system changes
  once and in order (`/usr/lib/lordos/migrate`, `packaging/migrations/`), so skipping versions
  converges to the same state; each user's settings get the same treatment at login
  (`sdk/settings.js`). The first two enable per-app network permissions where they were left off,
  and keep root's SSH key login on servers upgraded from 0.8.0 (0.8.1 turns root login off).
- **Local repositories in the package engine:** a `file:/path` source (a disk or a USB stick) is
  read like a download, as `nobody`, and checked the same way.
- **`tools/diag/keylag.sh`: where does the typing delay come from?** In two minutes it reports the
  composition mode, the VM and its guest tools and Chromium's complaints, and with
  `lordos.inputdebug=1` on the kernel line (one boot, root only) it times each stage of a key in
  ms: read by `lord-server`, delivered to the app, the app's answer, on screen. The trace holds
  timings only (no key, character or modifier), only for keys sent to Linux apps (never LordOS's
  own fields, the Terminal, Passwords, login or lock), in a 0600 file in the session's runtime
  folder, and stops after 120 s ([docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)).
- **`verify-board` checks Bluetooth and the BPF LSM** on a freshly flashed board: the controller on
  its UART, `bluetoothd`, the SCO helper, the board address, `bpf` in the LSM list, the kernel's
  BTF and `lord-netperm`.

### Changed

- **Monitor → Network: a fluid traffic chart.** The sparse per-second bars are now a continuous
  mirrored strip for the last 60 s: sent above the baseline, received below, one bar per second on
  a faint track, scrolling smoothly at 4 samples per second, auto-scaled, with the minute's totals
  as pills. The selected app gets the same chart, each app row a small live activity indicator, and
  the summary shows "↓ received · ↑ sent" per app and destination
  ([docs/MONITOR.md](docs/MONITOR.md#network)).
- **Monitor → Network: the map shows which way the traffic flows.** Dots travel along each arc,
  sent from "This computer" to the place and received back, more and faster with the rate; idle
  arcs are dimmed. Reduce motion shows still markers instead; the animation runs at 12 frames per
  second, only on screen, and stops when the window is minimized.
- **More audio headroom in virtual machines.** When LordOS runs in a VM, emulated sound outputs
  get 8 periods of 1024 frames, 8192 frames of headroom and interrupt-driven scheduling (a
  WirePlumber rule that only matches in a VM; real hardware keeps its low latency). On VMware this
  stopped YouTube stuttering in Chromium ([docs/SOUND.md](docs/SOUND.md#virtual-machines-081)).
- **Background work yields to the desktop after login.** Mail sync runs at nice 19 with idle I/O
  and the thumbnail worker at the lowest I/O priority, so they don't compete with sound and the
  first windows.
- **The input level meter in Settings → Sound** reads a normal 48 kHz stream instead of a 25 Hz
  peak stream, which in PipeWire ran as a node with a quantum of 1.
- **The LordOS Raspberry Pi kernel gains the BPF LSM, BTF and Yama** (`6.18.57-2+lordos`, same
  Raspberry Pi source as 0.8.0's `-1`): `CONFIG_BPF_LSM`, `CONFIG_DEBUG_INFO_BTF` (from `pahole`;
  modules stripped, no debug package) and `CONFIG_SECURITY_YAMA`. The active LSM list on the Pi is
  now `capability,landlock,yama,bpf`.

### Fixed

- **Typing no longer lags in Chromium and Firefox on GPU composition.** A Linux app's new frame is
  only a texture on the GPU path, and a display with no other change was not flipped, so a typed
  character appeared only when something else on the screen moved (up to ~1 s later; Firefox
  looked frozen), and Chromium logged "buggy presentation feedback". Every GPU display now presents
  an app's new content in the next frame; a frame shown by a modeset gets its presentation feedback
  at once; and with nothing drawn (screen off, session away from the monitor) apps still get their
  frame callbacks once a second. Measured with Chromium: p50/p95 from the key to the screen
  949/1866 ms before, 18/25 ms after; also in 0.8.0. Seen on VMware, reproduced on Proxmox
  ([docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)).
- **Linux app windows are no longer black after the login screen or a lock.** With GPU
  composition, coming back to the monitor creates a new GPU context, but each window's buffers were
  still drawn with their textures from the old one: Chromium's window stayed black while its audio
  kept playing. Imports now belong to one context and are made again, windows keep
  their last frame while the session is off the monitor, and apps get the new dmabuf formats
  ([docs/GPU.md](docs/GPU.md#when-the-gpu-context-is-re-created)).
- **Monitor → Network counts all of an app's traffic, UDP and QUIC included.** Per-app bytes came
  only from the TCP sockets open at that moment, so UDP — and with it QUIC: HTTP/3, a browser
  playing a video — counted nothing, and a closed connection took its bytes with it (a browser
  streaming music showed 13 KB). `lord-netperm` now counts every packet of each app's sockets in
  the kernel (two `cgroup_skb` programs, both directions, loopback excluded) and sends bytes and
  rates per app and per address every second: 98.7–98.8 % of the interface's counters in the
  tests (an HTTP/3 download, a browser on a video site), about 0.5 µs per packet and no measurable
  cost on TCP ([docs/FIREWALL.md](docs/FIREWALL.md#the-programs)).
- **The menu bar names a Linux app, not its window.** Next to the crown it showed the window title
  (for a browser, the whole page title); it now shows the app's short
  name, "Chromium", in every language. The Dock tooltip and Linux app notifications use the same
  short name; a real translation of the name (e.g. "Archivos") still shows, and a window without a
  `.desktop` file is named after its app id. The window's own title bar keeps the title.
- **Menus are always above the Dock.** With the Dock on the left, the crown menu opened underneath
  it and the Dock took its clicks; select lists inside apps (Passwords' category list) were drawn
  under the form fields after them. The desktop now has one stacking order, in layers (Dock < menu
  bar < fullscreen < launcher < menus and popovers < sheets < notifications < tooltips < drag
  images < system prompts), and clicks follow it, in every Dock position, light and dark, RTL and
  the Classic theme ([docs/LAYERS.md](docs/LAYERS.md)).
- **No lighter band in the menu bar after a menu or the Control Center closes.** The menu bar's
  background blur read the screen around it, and outside the repainted area that still held the
  bar's previous frame, so the repainted part came out lighter until something else redrew the bar.
  Now a change that touches a blurred surface, or the margin its blur reads, repaints the whole
  surface (the GPU path composites the same canvas; `engine-test` checks it against a full
  repaint).
- **The Network tab's detail panel no longer hides values under its scroll bar.** The panel keeps
  a strip for the bar, and a label and value that don't fit on one line go on two instead of
  running over the next row (es/en/pt, right to left, minimum window size).
- **The live ISO boots with legacy BIOS again.** 0.8.0 triple-faulted on VMware (and hung at the
  boot menu on QEMU's VMware-compatible display) when booting with BIOS firmware: GRUB's graphical
  terminal corrupted its own memory at 640×480 with the theme's proportional font. The theme now
  uses GRUB's fixed-width font for the terminal and BIOS boots ask for 1024×768 first; UEFI is
  unchanged. Installed systems get the same theme fix
  ([docs/ISO.md](docs/ISO.md#firmware-and-displays)).
- **No silent black screen without a KMS display.** When there is no display device with kernel
  modesetting (for example QEMU's VMware-compatible display), the text console now says so and
  suggests a display that works; `vmwgfx` only loads on VMware itself, so the console stays
  visible elsewhere.

### Security

- **"No Bluetooth" for Linux apps is enforced on the Raspberry Pi 5** (a known issue in 0.8.0):
  `lord-netperm` loads its Bluetooth socket program there as on a PC (`npverify-test` 37/37 on the
  board), and a process in a restricted app's scope gets `EPERM` from `socket(AF_BLUETOOTH)` while
  the same call outside it works.
- **`kernel.yama.ptrace_scope = 1` applies on the Raspberry Pi 5:** 0.8.0's Pi kernel had no Yama,
  so any process could attach to another of the same user there.
- **Root can't log in over SSH by default.** The `lordos` package ships
  `/etc/ssh/sshd_config.d/10-lordos.conf` with `PermitRootLogin no`, for the new SSH switch and for
  an SSH server installed any other way; a server upgraded from 0.8.0 that is administered as
  root with a key keeps key-only root login (see Upgrading).

- **On the Raspberry Pi 5, pairing a Bluetooth device and a headset's audio have not been tested

- **No metered-connection setting yet:** turn off Store → Updates → Check for updates automatically
  on a metered link.
- The other known issues of 0.8.0 still apply, except the two fixed above (the Pi 5's "No
  Bluetooth" and the built-in updater).

### Upgrading

- **From 0.8.0 (once):** run `curl -fsSL https://lordos.org/install.sh | sh` again (a system

## [0.8.0-beta] - 2026-10-18

LordOS is a free GNU/Linux distribution based on Debian 13 ("trixie") with its own desktop
environment. Debian provides the kernel, the drivers, Mesa, PipeWire, CUPS, BlueZ and every
package in the archive, with Debian's security updates. On top of that LordOS ships its own
graphical layer: a display server and Wayland compositor written in C that drives the screen and
input straight from the Linux kernel, its own interface engine running React, a full desktop and
29 native apps. GTK, Qt and other Wayland apps (Chromium and Firefox are preinstalled) open as
ordinary windows next to the native ones.

This is the **first public release**. It documents everything LordOS has today, not only what
changed since the last internal build. It is a beta: most of it works and is tested in virtual
machines, but some parts have not been tested on real hardware yet (see
[Known issues and limitations](#known-issues-and-limitations)). The project paper,
[docs/PAPER.md](docs/PAPER.md), gives the big picture.

### Highlights

- **Light enough for modest hardware.** The whole system idles at **465–487 MB of RAM** and
  **99 % idle CPU**, the live system boots to the desktop in **16.3 s**, and `lord-server` (the
  display server with the whole desktop) uses **32–36 MB** (measured in the final ISO test, see
  [docs/ISO.md](docs/ISO.md)).
- **A desktop of its own, built on Debian and Wayland.** Its own display server and Wayland
  compositor in C, its own React interface engine, two themes, a Dock, search, a clipboard
  history, several displays with sharp HiDPI, and smooth window moving even without a GPU.
- **Private by design.** Third-party apps run sandboxed (Landlock, seccomp, cgroup v2) behind a
  permission broker, with system-drawn prompts for the camera, microphone, files, screen and
  network. Passwords and other sensitive windows are black in screenshots, recordings and the
  remote desktop.
- **A visible, per-app firewall.** Allow or block the network per app, by domain, address or
  network, enforced in the kernel with cgroup BPF, and see every app's connections on a world map
  in Monitor. Linux apps can also be denied the camera, microphone, USB, Bluetooth, screen,
  notifications and your files.
- **29 native apps.** Files, Terminal, Text Editor, Notes, Mail, Calendar, Contacts, Reminders,
  Passwords, PDF Viewer, Photos, Player, Camera, Recorder, Screenshots, Monitor, Disks, Backups,
  Store and more, in English, Spanish and Portuguese, right to left included.
- **Install it your way.** A live and installable ISO for 64-bit PCs (UEFI and BIOS), a
  Raspberry Pi 5 image, or one command on an existing Debian 13. Every release file is listed in
  an Ed25519-signed `SHA256SUMS` and comes with an SPDX SBOM.
- **Every language, every script.** Full Unicode bidi, Arabic, Indic and about 80 more complex
  scripts shaped by our own engine, and Korean, Japanese and Chinese input methods.

#### Privacy and security

- **App sandbox** of our own, without Flatpak, bubblewrap or firejail: Landlock, a seccomp-bpf
  allow list, `no_new_privs`, dropped capabilities and a cgroup v2 scope per app
  ([docs/PRIVACY.md](docs/PRIVACY.md)).
- **Each `.lpk` app as its own process** (`lord-server --app <id>`), talking to the desktop only
  through a broker that checks every call; a malicious test app fails at everything at run time.
- **Per-app permissions** with prompts drawn by the system (not the app), stored where the app
  can't write, managed in Settings → Privacy, and green/orange dots while the camera or microphone
  is in use. Revoking the camera or microphone stops it at once.
- **Powerbox file picker:** an isolated app only gets the file the user picked, never the folder.
- **Protected windows:** Passwords and other sensitive windows are black in screenshots,
  recordings, the remote desktop and thumbnails.
- **Package signing:** `.lpk` apps signed with Ed25519 (our own SHA-256 and Ed25519 code, tested
  against RFC 8032 and NIST vectors), trust levels in the Store, a signed catalog with
  revocation, "Modified by you" detection, "Restore original" and "Share my version"
  ([docs/SIGNING.md](docs/SIGNING.md)).
- **Sandboxed helpers:** the only programs that link Poppler and libarchive (`lord-doc`), FFmpeg
  (`lord-media`), the mail parsers (`lord-maild`) and the vault crypto (`lord-vault`) run with no
  network, no sockets and no exec, and work only on the file descriptors they are given.
- **Secret clipboard:** copied passwords stay out of the history and are cleared after 30 s.

#### Firewall

- **Per-app network rules enforced in the kernel** by `lord-netperm`, a root service with cgroup
  BPF programs (connect, sendmsg, bind, socket creation) and its own BPF loader. Rules can allow or
  block all traffic, a domain and its subdomains, an address, a network, the LAN only, or incoming
  connections ([docs/FIREWALL.md](docs/FIREWALL.md)).
- **Settings → Privacy → Network rules by app:** each app's default and its rules, in the order
  they win (the most specific rule wins), with when each last matched, and a sheet that checks
  what you type as you type it.
- **Monitor → Network:** a per-app switch, allowed and denied counters, recent destinations, and
  "Allow / Block this domain" prefilled with the name the system resolver gave for the address.
- **Restrictions beyond the network:** for LordOS apps, no camera, microphone, screen, USB,
  files, clipboard, Bluetooth or notifications, refused without a prompt and applied live. For
  Linux apps: no camera, no USB and no Bluetooth sockets (kernel device and LSM programs), no
  microphone (a PipeWire guard plus the ALSA capture nodes), no notifications, and "no access to
  your files" (its own user, mount and PID namespace plus Landlock, from the next launch).
- **No screen capture for Linux apps,** by design: the compositor offers no capture protocol,
  there is no X server and no screen-cast portal, and `/dev/fb*` is denied.
- **Cheap:** about 0.5 µs per UDP connect, no measurable cost on TCP connects or throughput, and
  nothing in the frame loop.

### Security

Hardening and findings fixed before this first release. The full review is in
[docs/SECURITY-REVIEW-0.8.0.md](docs/SECURITY-REVIEW-0.8.0.md); report vulnerabilities as
described in [SECURITY.md](SECURITY.md).

- **Firewall restrictions were stored but not enforced** for the camera, microphone, screen, USB,
  files, clipboard, Bluetooth and notifications. They are now enforced where each resource is
  handed out, beat any permission grant, and apply live (58 broker checks in
  `tests/broker_restrict_test.c`).
- **Escape through `systemd-run --user`:** a Linux app could leave its scope for the user manager.
  The programs now also cover each user's `user@<uid>.service`, with no exemption for the user's
  own audio services, which the app could otherwise move into.
- **App scopes are owned by root,** so a Linux app can no longer move itself to another cgroup.
- **"No access to your files" for Linux apps** now runs the app in its own user, mount and PID
  namespace: Landlock alone did not cover unix-socket `connect()` in kernel 6.12, so an app could
  have asked the session bus to start something outside the restriction. Its writable folders come
  only from its desktop id, never from fields a malicious `.desktop` file controls.
- **PipeWire guard identity** comes from the socket's kernel credentials; a forged
  `application.process.id` or an unresolvable client is treated as restricted (fail closed).
- **Microphone restriction** also covers recording straight from the sound card (ALSA capture
  nodes), not only through PipeWire.
- **Notifications:** only the bus itself can say who sent a notification; forged, failed or late
  answers drop it.
- **Permission prompts and file pickers** use ids generated by the server, so an app can't answer
  another app's prompt.
- **Mail:** HTML goes through our own sanitizer into native views (no web engine), remote content
  is blocked until asked, and the parsers run in a sandboxed helper with no network of its own;
  31,000+ checks including mutation fuzzing.
- **Installer:** every value is validated on the root side, the password travels over a
  socketpair (never argv), is hashed with yescrypt and wiped from memory.
- **Signed releases:** `SHA256SUMS` is signed with the LordOS Ed25519 release key, and the Debian
  installer refuses to install when the signature is missing or invalid.
- **Remote desktop** is off by default and only reachable after the owner turns it on.

Fixed from the security review before this release (high and medium findings; the numbers are
the review's, in [docs/SECURITY-REVIEW-0.8.0.md](docs/SECURITY-REVIEW-0.8.0.md)):

- **A malicious `.desktop` file could leave the "no access to your files" view** (#1, high): the
  working directory was entered before the private folders were mounted, so a relative path still
  reached the real session bus. The directory is now entered inside the view.
- **An app that couldn't be placed in its own scope still ran, unrestricted** (#2, high), for
  unusual desktop ids or when lord-sessiond was unreachable. Desktop ids are now limited to safe
  characters and length, and inside a LordOS session an app that can't be placed never starts.
- **The microphone guard failed open** (#3, high) when its client or node tables filled up or a
  permission list was too long. It now disconnects clients it can't follow and destroys streams it
  can't store.
- **A restricted app could record the microphone through a PulseAudio module** (#4, high), which
  ran as the unrestricted pipewire-pulse. Module loading is off (see "Changed").
- **A restricted Linux app could take over an unrestricted process of the same user with
  `ptrace`** (#5, high). Only descendants can be traced now (see "Changed").
- **Restricted Linux apps could escape through the user's own services** (#13, #37, high): two
  attempts to exempt "the real sound server" under `user@` were forgeable, because the user
  controls their own systemd manager. Nothing under `user@` is trusted for who it claims to be any
  more; apps restricted from the microphone, camera, USB or Bluetooth start in their own view
  instead (see "Changed"), and the desktop keeps its microphone.
- **"Open with" could hand an app protected folders** (#6, medium) such as `~/.config/autostart`,
  `firewall.json` or `~/.ssh` when a parent folder was opened, and **a symlink swapped in between
  the check and the grant** could redirect it (#10, medium). Writable grants never cover those
  folders, hard-linked files are read-only, and the grant is reopened without following symlinks
  and must still be the checked file.
- **Shared memory, terminals and caches of the session were reachable** from the files view (#7,
  #8, medium): it now has its own `/dev/shm`, its own pseudo-terminals and IPC namespace, and the
  font, shader and GStreamer caches are read-only. More folders that other programs run code from
  are protected (#9), and a missing `XDG_RUNTIME_DIR` no longer leaves the bus reachable (#11).
- **A USB microphone plugged in while a no-mic app ran** was open to it for a few seconds (#12,
  medium): every sound device not known to be playback-only is now denied in its scope.
- **A user process could pose as the sound server** to the microphone guard (#14, #15, #16,
  medium) with a nested cgroup or another PID namespace. Matching is now exact (cgroup path, sole
  process, root-owned binary, our PID namespace).
- **The last frame of another user's desktop could be read after a user switch** (#17, medium):
  lord-sessiond now removes the leaving session's framebuffers before handing the screen over.
- **Landlock's socket scoping failed open on older kernels** (#38, medium): the files view and the
  device view now require Landlock ABI 6 and refuse to start the app otherwise, with a notification.
- **Installer and release tools** (low): the verified package is reinstalled from a root-owned
  copy, a missing release key is an error, a validly signed older release can't downgrade an
  install, and the signing script refuses unexpected file names.

### Known issues and limitations

- **Xwayland is not supported:** apps that only speak X11 don't start (planned before 1.0).
- **Flatpak is not integrated** with the Store, the launcher or the sandbox.
- **The Raspberry Pi 5 image has not been booted on a board yet.** The build, the tests and the
  login screen are verified on the Pi 5 running from its own SD card, but the published image
  itself is still untested on hardware ([docs/RASPBERRY.md](docs/RASPBERRY.md)).
- **On the Raspberry Pi 5, "No Bluetooth" is not enforced for Linux apps:** the LordOS build of the
  Raspberry Pi kernel has no BPF LSM (`CONFIG_BPF_LSM`), so the Bluetooth socket program can't be
  loaded there (`lord-netperm` reports `"bluetooth":false`). The network rules and the other
  restrictions work as on a PC.
- **The clipboard restriction is not available for Linux apps:** the Wayland data device is not
  mediated per app.
- **BlueZ over D-Bus is not mediated:** a Linux app restricted from Bluetooth can't open Bluetooth
  sockets, but can still ask `bluetoothd` on the system bus to scan, pair and connect.
- **The `.lpk` signing key is still a development key.** Official app packages are signed with it
  until the final key replaces it; a signed LordOS app repository for the Store is not built yet.
- **Encrypted disks (LUKS) are untested:** the splash's password field has only been checked as a
  static preview, and Disks doesn't create LUKS or LVM volumes.
- **Secure Boot** has to be turned off on PCs (signing with a shim is pending).
- **Not yet tested on real hardware:** AMD and NVIDIA GPUs, laptop batteries, backlight and lid,
  real Bluetooth controllers, FIDO2 security keys, printers and scanners, WPA3 networks, and mail
  providers (OAuth is prepared but disabled).
- **Firewall:** no "ask" mode yet (it behaves as silent); domain rules don't see apps that resolve
  names with their own encrypted DNS (address rules, defaults and restrictions still apply); while
  a restricted app runs, the `systemd-run --user` protection restricts the whole user manager
  subtree, not only the escaped process.
- **Wayland:** drag and drop between apps, the primary selection, LordOS input methods inside Linux
  apps (`text-input`), `xdg-activation` and SVG app icons are pending.
- **Accessibility tools** (screen reader, zoom, high contrast) are not available yet.
- **No built-in updater for LordOS itself:** new versions come from GitHub Releases; Debian
  packages update from the Store.
- Switching to a text console (Ctrl+Alt+F2) doesn't work while LordOS runs; the remote desktop has
  no audio yet; 802.1X/WPA-Enterprise and DHCPv6 are not supported; GRUB shows about a second of
  black while it loads the kernel.

See the pending items in [docs/ROADMAP.md](docs/ROADMAP.md).

### Upgrading

This is the first public release, so there is nothing to upgrade from. To install it:

- **On a PC:** write `lordos-live-<version>-amd64.iso` to a USB stick (it is hybrid: `dd`, or any
  image writer in DD mode), boot it with Secure Boot off, try LordOS live, and open **Install
  LordOS** to install it to a disk. The whole disk is erased ([docs/ISO.md](docs/ISO.md)).
- **On a Raspberry Pi 5:** write `lordos-<version>-rpi5-arm64.img.xz` to an SD card or NVMe drive
  with Raspberry Pi Imager ("Use custom") ([docs/RASPBERRY.md](docs/RASPBERRY.md)).
- **On an existing Debian 13** (amd64 or arm64): run `curl -fsSL https://lordos.org/install.sh | sh`.
  It asks before changing anything; `--uninstall` removes LordOS again
  ([docs/INSTALL-DEBIAN.md](docs/INSTALL-DEBIAN.md)).

Later releases: on Debian, run the installer again, or install the new `.deb`.

### Verifying

Every release file is listed with its SHA-256 in `SHA256SUMS`, and `SHA256SUMS.sig` is the
Ed25519 signature of `SHA256SUMS` made with the LordOS release key. The public key is
`lordos-release.pub.pem` (in this release, in the repository at
`tools/release/lordos-release.pub.pem` and at https://lordos.org/lordos-release.pub.pem). Its
fingerprint (SHA-256 of the DER public key) is:

```
c7155b8e6bbbb180f907381994d06af76d333016cd6f3facf67cadd053ea108e
```

With OpenSSL 3, in the folder with the downloads:

```sh
openssl pkey -pubin -in lordos-release.pub.pem -outform DER | sha256sum   # must match the fingerprint
base64 -d SHA256SUMS.sig > SHA256SUMS.sig.bin
openssl pkeyutl -verify -pubin -inkey lordos-release.pub.pem -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig.bin
sha256sum -c --ignore-missing SHA256SUMS
```

`Signature Verified Successfully` and `OK` for each file you downloaded mean the files are the ones
we published. See [docs/SIGNING.md](docs/SIGNING.md).
